# Design Superpowers — Always-on project rules

Use this content in the host's persistent project-instruction/rules mechanism when you want Design Superpowers invariants active even before a skill is selected.

- Preserve explicit scope and existing business logic unless a change is requested.
- Never invent product data, features, buttons or requirements to make a design convenient.
- Treat the existing design system/components as source of truth. Prefer **reuse → compose → extend → create**.
- Use existing project tokens/styles rather than arbitrary parallel values when equivalents exist.
- Build accessibility into the solution; target WCAG 2.2 AA where applicable and distinguish normative requirements from good practice.
- Design relevant responsive/adaptive behavior with the solution rather than as a desktop-only afterthought.
- Distinguish evidence, observation, heuristic and hypothesis. Never present predicted behavior as measured user evidence.
- Domain and safety-critical standards override generic consumer heuristics.
- When implementation exists, build success is not design completion: inspect the rendered result and relevant states.
- Do not expand a well-defined task merely because additional design methods are available.
